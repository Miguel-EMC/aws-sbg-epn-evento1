Parte 1 · Lo básico que sí queremos enseñar

Mapa mental de AWS para principiantes

No buscamos profundidad de certificación. Cada concepto debe responder una pregunta concreta antes de pasar a la práctica.

1

Cloud Computing

Pregunta: ¿por qué alquilar infraestructura en lugar de comprarla?

Elasticidad, pago por uso, aprovisionamiento rápido.

2

Regiones

Pregunta: ¿en qué parte del mundo estoy desplegando?

Una región es una ubicación geográfica de AWS. Elegir región afecta latencia, disponibilidad de servicios y costos.

3

Availability Zones

Pregunta: ¿por qué una región tiene varias zonas?

Son ubicaciones físicamente separadas dentro de una región, útiles para diseñar alta disponibilidad.

4

IAM

Pregunta: ¿quién puede hacer qué?

Identidades, permisos, roles, MFA y principio de mínimo privilegio.

5

EC2

Pregunta: ¿qué es realmente “un servidor en AWS”?

Una máquina virtual con CPU, memoria, disco, sistema operativo y red.

6

Security Groups

Pregunta: ¿por qué mi servidor existe pero mi web no abre?

Firewall virtual asociado a recursos como EC2.

7

Costos

Pregunta: ¿qué puede generar cargos?

Tiempo de cómputo, almacenamiento, transferencia, IPs y otros recursos según servicio.

8

Responsabilidad

Pregunta: ¿qué asegura AWS y qué aseguro yo?

Introducción simple al modelo de responsabilidad compartida.

9

Limpieza

Pregunta: ¿qué hago cuando termino?

Detener/terminar recursos y comprobar que no queden servicios activos.

Regiones y AZ

Cómo explicarlo sin hacerlo pesado

“AWS no es una computadora gigante en un único lugar. AWS tiene regiones distribuidas por el mundo. Dentro de cada región existen varias Availability Zones físicamente separadas. Hoy elegiremos una sola región para que todos trabajemos igual.”

Ejemplo didáctico: una región ≈ ciudad/área geográfica; AZ ≈ centros de datos separados dentro de esa región. Aclarar que es una analogía, no una equivalencia literal.

IAM rápido

Configuración y buenas prácticas

  • Explicar por qué la cuenta root se usa solo para tareas que realmente la requieren.
  • Mostrar MFA y recomendar habilitarlo.
  • Diferenciar usuario, grupo, rol y política.
  • Explicar mínimo privilegio: dar solo los permisos necesarios.
  • No compartir contraseñas ni access keys.
  • No subir secretos a GitHub.
“IAM responde una pregunta: ¿quién puede hacer qué sobre qué recurso? Si alguien necesita leer S3, no significa que deba poder borrar EC2.”
Costos

Cloud sin sorpresas 💸

  • Pago por uso no significa “todo es gratis”.
  • Free Tier / créditos dependen de condiciones y límites.
  • Un Budget es una alerta, no un interruptor automático de todos los gastos.
  • Revisar Billing / Cost Explorer / Budgets.
  • Etiquetar recursos ayuda a saber qué pertenece al taller.
  • Eliminar recursos al finalizar.
“La mejor cost practice para un principiante es saber qué creó, cuánto tiempo lo va a usar y cómo eliminarlo.”
Buenas prácticas

Checklist del día 1

  • MFA habilitado.
  • Región definida para el taller.
  • Mínimo privilegio en IAM.
  • Puertos abiertos solo cuando hacen falta.
  • No usar 0.0.0.0/0 innecesariamente fuera del ejercicio.
  • Evitar secretos en código.
  • Usar nombres/tags claros para recursos.
  • Revisar y limpiar recursos.
Guion minuto a minuto

Agenda propuesta · 2 h 15 min

0:00–0:10

1. Bienvenida + AWS Student Builder Group

Presentación rápida del Core Team, objetivo del grupo, reglas del evento y sondeo inicial.

“Hoy queremos que entiendan AWS desde la base y terminen con algo publicado por ustedes. No vamos a empezar con 40 servicios ni con una arquitectura imposible.”
0:10–0:25

2. ¿Qué es cloud y qué es AWS?

On-premise vs cloud, pago por uso, elasticidad, servicios administrados. Mostrar consola y explicar que AWS agrupa servicios por categorías.

0:25–0:37

3. Regiones, Availability Zones y elección de ubicación

Mapa de regiones. Explicar región, AZ, latencia y por qué todos usarán la misma región durante el workshop.

Mini pregunta: “Si mis usuarios están en Latinoamérica, ¿qué cosas considerarían antes de elegir una región?”
0:37–0:52

4. IAM y seguridad básica

Root, MFA, usuarios, roles, políticas y mínimo privilegio. Mostrar IAM en consola sin crear una estructura compleja.

Objetivo: que comprendan que permisos y autenticación son parte del diseño, no algo que se agrega al final.
0:52–1:05

5. Costos, Free Tier, Budgets y limpieza

Explicar qué puede generar costos, cómo revisar Billing, qué hace un Budget y por qué todo recurso del taller debe eliminarse.

“Una alerta de presupuesto ayuda a enterarte; no reemplaza el hábito de revisar y limpiar recursos.”

EC2 → IP pública → intento fallido → Security Group → HTTP/80 → Instance Connect → Nginx → HTML.

Momento clave: dejar HTTP cerrado al principio para que experimenten el fallo y luego entiendan qué cambia al abrir el puerto 80.
1:55–2:05

Cada participante modifica su página y envía su IP/URL. Mostrar varias en vivo.

2:05–2:10

8. Builder Center + próximos pasos

QR/enlace a Builder Center, recursos recomendados y adelanto del Evento 2.

2:10–2:15

9. Limpieza guiada + CSAT

Terminar EC2 todos juntos, comprobar recursos y compartir encuesta.

Parte práctica

Hands-on completo

Paso 0 · Check previo

  • Todos en la región definida.
  • Cuenta/lab/sandbox funcional.
  • Nombre del recurso: epn-evento1-tuNombre.
  • Tag sugerido: Event=EPN-Event-01.

Paso 1 · Crear EC2

  1. Abrir EC2 → Launch instance.
  2. Nombre claro.
  3. Amazon Linux.
  4. Tipo pequeño permitido por el entorno elegido.
  5. Red por defecto para simplificar el primer taller.
  6. No habilitar HTTP todavía.
  7. Lanzar instancia.

Paso 2 · Checkpoint “¿por qué no carga?”

Copiar la IPv4 pública y abrir http://IP_PUBLICA. La web todavía no debe responder porque aún no existe servidor web y/o HTTP no está permitido.

Paso 3 · Entrar con EC2 Instance Connect

Evitar SSH local en este primer taller para no mezclar problemas de claves, terminales y sistemas operativos.

Paso 4 · Instalar Nginx

sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx --no-pager

Paso 5 · Abrir HTTP/80

Editar el Security Group y agregar HTTP TCP/80. Para el ejercicio introductorio se puede permitir tráfico web público y explicar claramente qué significa el origen configurado.

Paso 6 · Crear la página

sudo tee /usr/share/nginx/html/index.html > /dev/null <<'EOF'
<!DOCTYPE html>
<html lang="es">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Mi primera web en AWS</title>
  <style>
    body{
      font-family:system-ui;
      background:#0b1220;
      color:white;
      max-width:760px;
      margin:80px auto;
      padding:24px;
    }
    h1{color:#38bdf8}
    .tag{display:inline-block;background:#ff9900;color:#111;padding:6px 10px;border-radius:999px}
  </style>
</head>
<body>
  <span class="tag">AWS Student Builder Group at EPN</span>
  <h1>Hola desde AWS 🚀</h1>
  <p>Soy TU_NOMBRE y esta es mi primera página corriendo en EC2.</p>
  <p>Hoy aprendí sobre regiones, IAM, costos, EC2 y Security Groups.</p>
</body>
</html>
EOF

Paso 7 · Personalizar

Cambiar nombre, carrera, frase, colores y contenido. Evitar descargar frameworks o dependencias innecesarias.

Paso 8 · Cloud Gallery

Formulario: nombre + carrera + IP/URL + “qué aprendí hoy”. Mostrar varias páginas en vivo.

Paso 9 · Limpieza obligatoria

  • Terminar la instancia EC2.
  • Confirmar que no queden instancias Running.
  • Revisar recursos adicionales creados durante el taller.
  • Volver a Billing/Budgets como cierre de aprendizaje.

  • ✅ Tengo IPv4 pública.

  • ✅ Nginx responde.
  • ✅ Personalicé mi HTML.
  • ✅ Envié mi URL a la galería.
  • ✅ Terminé mi instancia.

Entorno de práctica

Antes de anunciar requisitos

Preferido: usar un entorno preconfigurado, Builder Lab o sandbox que soporte el ejercicio. Así se reduce la barrera de cuenta/tarjeta para principiantes.

Si usan cuentas AWS personales: mandar la guía con una semana de anticipación, hacer una sesión corta de ayuda, usar un recurso pequeño, no incluir Elastic IP en el primer evento y limpiar todo al cierre.
